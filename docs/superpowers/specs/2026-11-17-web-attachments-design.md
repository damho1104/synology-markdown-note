- 작성일: 2026-11-17 (KST)
- 브랜치: `feature/web-attachments`
- 기준: `develop`의 `c78a01ca69bdca3592e6f40de4ed2bf8179bf743`
- 사용자 요청: 추가 개발 2번(웹 이미지 붙여넣기·파일 첨부)을 우선 진행하기 위한 feature 브랜치와 설계 문서 작성.
- 아래 1차 범위, API, 용량·보관 기본값은 현재 코드에 근거한 구현자 제안이며 사용자 확정 요구사항과 구분한다.

## 1. 목적과 완료 모습

웹에서 스크린샷을 붙여넣거나 파일을 선택한 뒤 현재의 자동 저장만으로 NAS 노트까지 작성할 수 있게 한다.
맥 앱이나 Note Station으로 돌아가 첨부하는 작업을 줄인다.
본문·기존 첨부·수식·원문 봉투를 보존하며, 응답 유실을 업로드 실패로 단정해 중복 첨부하지 않는다.

예시: Markdown 회의록의 커서 위치에 스크린샷을 붙여넣으면 진행 상태가 나타난다.
서버 임시 보관 완료 후 이미지가 보이고, 자동 저장 및 NAS 재조회가 끝나면 ‘NAS 저장됨’으로 표시된다.
PDF를 선택하면 같은 위치에 다운로드 링크가 들어가며 정보 패널에도 첨부가 표시된다.

## 2. 확인한 현재 구현

| 코드 | 현재 역할과 제약 |
| --- | --- |
| `web/frontend/src/Workspace.tsx` | CodeMirror 편집, 800ms 자동 저장, IME 대기, 초안 보관, 저장 중 추가 입력 재기준화, 불확실 쓰기 차단. 첨부 패널은 목록·다운로드 제공 |
| `web/frontend/src/NotePreview.tsx` | `attachment://UUID`와 검증된 바인딩을 이용해 인증된 API에서 이미지 로딩 |
| `web/backend/synonote_web/main.py` | `WriteInput`, 노트 생성·수정, CSRF, 계정별 쓰기 저널·생성 영수증. 첨부 GET은 노트의 실제 첨부 소속을 검사 |
| `web/backend/synonote_web/nas.py` | `_mutate_markdown`에 multipart 업로드 존재. 현재 MIME 선택은 PNG/Markdown 전용. `write_markdown`은 새로운 일반 첨부 참조를 거절하며 수식·원문 전송만 지원 |
| `web/backend/synonote_web/attachment_html.py` | 검증된 UUID→NAS 첨부 ID 바인딩을 NAS용 HTML의 `ref`/링크로 치환 |
| `web/backend/synonote_web/store.py` | NAS URL·계정 기반 owner, 암호화된 의도/생성 영수증, 대상 쓰기 잠금. 일반 파일 임시 저장은 없음 |
| `web/backend/synonote_web/compat/source_envelope.py` | 맥·CLI와 공유하는 원문 봉투 및 attachment_bindings 계약 |

현재 원문 저장은 staging 원문 → 수식 첨부 → 본문 → 최종 원문 및 정리 → 재조회 순서다.
일반 첨부는 이 계약 안에 추가한다. 별도 무잠금 NAS 업로드 경로를 만들지 않는다.
NAS multipart 일반 파일 계약과 실제 Note Station 호환성은 아직 이 작업에서 검증하지 않았다.

## 3. 1차 범위 제안

### 포함

- 새 Markdown 노트와 편집 가능한 기존 Markdown 노트.
- 이미지 클립보드 붙여넣기, 편집기로 파일 드롭, ‘파일 추가…’ 버튼.
- 여러 파일은 입력 순서대로 큐에 넣고, 네트워크 전송은 최대 2개 동시 처리.
- PNG/JPEG/GIF/WebP 중 서버가 형식을 검증한 파일은 본문 이미지로 삽입.
- PDF/ZIP/문서 등 그 외 파일은 첨부 다운로드 링크로 삽입.
- 업로드 대기·임시 보관 완료·NAS 저장 중·완료·실패·결과 확인 필요 상태.
- 저장 전 첨부 취소와 다시 시도, 서버 재시작 후 임시 첨부 상태 조회.
- 맥 앱·Note Station에서 새 첨부를 확인하고 다시 웹에서 읽는 왕복 검증.

### 후속 범위

- 기존 HTML 노트에 새 첨부 삽입, 암호화·읽기 전용·휴지통 노트 첨부.
- NAS에 이미 저장된 일반 첨부의 삭제와 자동 미사용 첨부 수거.
- 브라우저 오프라인 파일 저장, 외부 URL 이미지 대리 다운로드, 폴더/재귀 업로드.
- 이미지 편집·리사이즈·HEIC 변환·SVG 인라인 렌더링·PDF 인라인 미리보기.

본문 링크를 지우는 것과 NAS 파일을 삭제하는 것을 구분한다.
이미 저장된 파일은 본문 참조를 지워도 첨부 패널에 남는다. 기존 첨부 보호 정책을 유지한다.

## 4. 접근 방식 비교와 제안

| 방식 | 장점 | 비용·위험 |
| --- | --- | --- |
| 파일 선택 즉시 NAS 첨부 | 서버 임시 보관이 작음 | 본문 자동 저장과 버전 경쟁, 새 노트 사전 생성, 응답 유실 시 중복 첨부 처리 복잡 |
| 저장 JSON에 base64 포함 | 별도 업로드 API가 적음 | 약 1/3 전송량 증가, 큰 초안·메모리·재전송 부담. 수식용 경로를 일반 파일로 확대하기 부적합 |
| 서버 임시 보관 후 노트 저장에 결합 | 파일 전송과 NAS 쓰기 경계 분리, 기존 잠금·영수증 재사용 | 임시 데이터의 격리·암호화·보관 및 회수 필요 |

세 번째 방식을 권장한다. 업로드 완료는 ‘웹 서버 임시 보관 완료’이며 NAS 저장 완료를 뜻하지 않는다.
현재 인증·자동 저장·원문 봉투·읽기 검증을 재사용하고, 새 프런트 상태와 파일 보관 코드는 분리한다.

## 5. 사용자 흐름과 편집 상태

1. 파일 입력 당시 계정·draft_id·현재 노트·CodeMirror 문서 세대와 삽입 위치를 고정한다.
2. 클라이언트가 즉시 크기/개수 오류를 알려 주고 첨부 큐를 표시한다. 서버 검사가 최종 기준이다.
3. 편집기에 파일이 포함된 paste/drop이면 기본 처리를 막아 이미지와 텍스트가 이중 삽입되지 않게 한다.
   파일 없는 일반 텍스트·Markdown 붙여넣기는 기존 동작을 유지한다.
4. 임시 업로드 중에도 본문 편집은 허용한다. 위치는 CodeMirror transaction을 따라 이동하는 bookmark로 추적한다.
   IME 조합 중 삽입은 조합 종료까지 보류한다. 원시 offset만 나중에 재사용하지 않는다.
5. 임시 보관이 확인된 파일만 `![대체 텍스트](attachment://UUID)` 또는
   `[파일명](attachment://UUID)`로 한 번 삽입한다. Markdown 이름/대체 텍스트는 이스케이프한다.
6. 업로드·IME 작업이 모두 끝나면 기존 800ms 자동 저장을 재개한다.
   저장 snapshot에는 본문과 그 snapshot에 참조된 첨부 manifest를 함께 고정한다.
7. NAS 검증 성공 후 해당 snapshot의 파일만 완료 처리한다. 저장 중 추가 입력/추가 파일은 다음 저장에 남긴다.

초안에는 draft_id, UUID 참조, upload_id, 상태만 저장한다. 원본 바이너리·base64·object URL은 sessionStorage에 넣지 않는다.
미리보기 object URL은 메모리에서만 쓰고 제거/언마운트 시 해제한다. 다시 열면 인증된 임시 파일 API를 사용한다.
노트 전환·로그아웃은 기존 dirty 저장 게이트를 확장해 미완료 업로드를 먼저 처리하거나 명시적으로 취소해야 한다.
늦은 응답은 다른 계정/노트/새 초안에 삽입하지 않는다. 취소된 upload_id의 완료 응답도 무시한다.
브라우저 강제 종료 전 서버가 수신하지 못한 파일은 재선택이 필요하다고 표시한다.

실패한 파일을 조용히 건너뛰고 성공으로 표시하지 않는다. 해당 파일 재시도 또는 취소 후 저장을 이어간다.
파일 삽입을 실행 취소하면 참조는 제거하지만 redo를 위해 임시 바이트는 즉시 삭제하지 않는다.
본문에 참조가 없는 임시 파일은 NAS 전송 대상에서 제외한다.

## 6. 임시 파일 저장과 API 제안

### 식별과 격리

- 서버의 owner(NAS URL+사용자)와 클라이언트 draft_id(UUID)를 조합한다.
- 기존 노트는 note_id, 새 노트는 client_request_id와 메모장 ID에 귀속한다.
- 새 노트가 NAS ID를 얻으면 동일 쓰기 트랜잭션에서 귀속 관계를 확정한다.
- 업로드 UUID를 경로나 권한 증명으로 사용하지 않는다. 모든 읽기/조회/취소에서 owner와 draft 귀속을 확인한다.
- 여러 탭의 초안은 draft_id를 분리한다. 타 노트 첨부를 UUID만 바꿔 가져올 수 없게 한다.

### 제안 API

| API | 역할 |
| --- | --- |
| `PUT /api/drafts/{draft_id}/uploads/{upload_id}` | `application/octet-stream` 본문으로 단일 파일 수신. query에 note_id 또는 client_request_id와 notebook_id, 헤더에 X-Upload-Name(URI 인코딩)과 X-Upload-Size(바이트). NAS 변경 없음 |
| `GET /api/drafts/{draft_id}/uploads/{upload_id}` | 임시 업로드 상태·UUID·크기·서버 SHA-256·표시 유형 조회. 응답 유실 후 복구 |
| `GET /api/drafts/{draft_id}/uploads/{upload_id}/content` | 인증·owner 검사 후 미리보기 또는 다운로드 |
| `DELETE /api/drafts/{draft_id}/uploads/{upload_id}` | 쓰기에 사용 중이 아닌 임시 파일 취소. 보류 확인을 마친 임시 복사본도 명시적으로 폐기할 수 있다. NAS 파일 삭제 없음 |
| 기존 `POST /api/notes`, `PUT /api/notes/{note_id}` | draft_id와 참조된 upload manifest를 추가해 기존 저장 경로로 반영 |

모든 변경 API는 기존 Origin/CSRF 검사를 적용한다. 읽기는 기존 세션 만료·회전 규약을 따른다.
PUT은 같은 upload_id+동일 내용 재호출 시 같은 결과를 반환한다. 다른 내용/귀속으로 재사용하면 409로 거절한다.
서버가 최종 SHA-256을 계산한다. HTTP 내부망에서 WebCrypto가 없더라도 입력이 가능해야 한다.
업로드 응답 유실 시 먼저 GET으로 조회한다. 서버의 receiving lease가 살아 있으면 기다리며 다른 파일로 재사용하지 않는다.
서버 재시작으로 끝나지 않은 수신은 partial을 폐기하고 같은 내용으로 재시도할 수 있게 명확히 구분한다.

### 저장 방식과 기본값 제안

- 기존 SQLite와 암호화 키를 재사용한다. 파일을 청크 단위로 암호화해 임시 저장하고, 수신을 완료한 파일만 원자적으로 게시한다. NAS 전송과 해시 확인도 순차적으로 처리한다.
- 파일당 50MB(50,000,000바이트)를 허용한다. 1바이트라도 초과하면 브라우저와 서버에서 거절하고, 서버는 실제 수신량도 검증한다. 초안 150MB, 계정 300MB, 설치 전체 1GB를 임시 보관 기본 한도로 둔다.
- 동시 receiving을 포함한 크기/슬롯 예약을 SQLite 트랜잭션으로 확보한다. 계정당 수신 동시 2개, 설치 전체 8개를 상한으로 두어 메모리를 제한한다.
  Content-Length 없이도 스트리밍 수신 중 실제 바이트를 세고 상한 초과 즉시 중단한다.
- 미참조·미사용 임시 파일은 마지막 사용 후 7일에 만료한다. 조회로 보관 기간을 무한 연장하지 않는다.
  완료된 파일은 NAS 저장 성공 후 바이너리를 회수할 수 있지만, 동일 요청 판별용 메타데이터/영수증은 별도로 유지한다.
- 진행 중·확인 전 불확실 쓰기에 pin된 파일은 TTL/로그아웃/취소로 삭제하지 않는다.
  보류 확인 뒤에는 `reviewed` 상태로 7일 동안 다운로드하거나 직접 폐기할 수 있다. 기한이 지난 바이너리는 다음 업로드 예약 시 회수한다.
  회수 이후에도 기존 업로드 ID의 재사용 금지 기록을 보존한다. NAS 파일과 생성 영수증은 유지한다.
- DB 삭제 후 SQLite 파일 크기가 즉시 줄지 않을 수 있다. 보관량은 live bytes로 계산하고 기존 백업·DB 유지보수 안내를 따른다.
- 용량 초과·디스크 부족은 명시적 오류로 반환한다. 기존 노트 자동 저장까지 조용히 성공 처리하지 않는다.

용량·보관 기본값은 코드 상수로 중앙 관리하고 테스트한다. 환경변수 추가는 실제 운영 요구가 생길 때 결정한다.
브라우저 파일은 본문 스트림에서 직접 읽는다. NAS의 Note Station API에 전송하는 단계에서만 multipart를 사용한다.

## 7. NAS 저장 트랜잭션 확장

1. 기존 생성 영수증을 먼저 검사한다. 이미 완료된 같은 생성 요청은 임시 바이너리 회수 이후에도 결과를 반환해야 한다.
2. NAS의 현재 버전·편집 가능 여부, owner/draft/노트 귀속, 파일 크기·SHA-256·준비 상태,
   본문의 새 참조와 manifest의 정확한 일치를 mutation 전에 검증한다.
   기존 서버 첨부는 기존 바인딩으로, 새 참조만 검증된 임시 manifest로 허용한다.
3. `Store.start_write`의 대상 잠금/요청 의도와 동일 트랜잭션으로 첨부를 pin한다.
   요청 hash는 고정된 manifest(upload_id·참조·내용 hash·이름·크기·유형)를 포함한다.
   같은 idempotency key로 다른 manifest를 보내면 거절한다.
4. 기존 staging 원문과 원본 HTML을 보존한다. 일반 첨부를 정해진 순서로 업로드하고 각 업로드 후 버전·새 파일 ID를 재조회한다.
   `_mutate_markdown`은 임의 파일의 명시적 MIME을 받을 수 있도록 확장한다. 기존 PNG/Markdown 호출과 호환해야 한다.
5. 파일명만으로 새 첨부를 찾지 않는다. 작업 UUID 기반 전송 식별자와 사전/사후 ID 집합, 파일 다운로드 SHA-256을 함께 검사한다.
   같은 이름 파일 둘도 UUID별로 독립 매핑한다. 사용자 이름은 표시 메타데이터로 보존하고 서버 원시 파일명은 충돌 없이 관리한다.
   Note Station/맥에서 보일 실제 이름의 제약은 실제 NAS multipart 검사 후 확정하며 이름만으로 기존 파일을 삭제하지 않는다.
6. 검증된 UUID→NAS ID 바인딩을 만든 뒤 HTML을 렌더링·치환한다.
   현재 write_markdown의 초기 bind_html을 그대로 두면 새 참조가 없다고 실패하므로, 로컬 preflight와 최종 NAS 바인딩 단계를 분리한다.
7. 기존 수식 처리와 원본 보존 블록을 유지하면서 본문을 저장한다.
   최종 SourceEnvelope에 기존 바인딩+새 바인딩을 기록한다. 호환 포맷 변경이 필요하면 맥·CLI 동작 검증 전에는 도입하지 않는다.
8. 최종 재조회로 제목·본문·원문·바인딩·일반 첨부 바이트·기존 첨부 보존·수식 보존을 확인한다.
   그 이후에만 쓰기/생성 영수증과 프런트 상태를 저장 완료로 확정한다.

바이너리 회수 후 같은 파일을 다시 업로드하지 않도록 committed 업로드 ID→노트/파일 ID 매핑을 유지한다.
동일 파일 참조를 포함한 다음 자동 저장에서는 기존 NAS 바인딩을 사용한다.

## 8. 장애·충돌·취소

| 상황 | 처리 |
| --- | --- |
| 브라우저→웹 서버 업로드 실패 | NAS 미변경. 상태 조회 후 동일 upload_id로 안전한 수신 재시도 |
| 임시 보관 완료 후 새로고침/서버 재시작 | 초안 토큰으로 상태 조회 후 참조·미리보기 복구. 자동 NAS 재전송 없음 |
| mutation 전 버전 충돌·권한 변경 | 원문·임시 첨부 유지, 충돌 화면. pin 해제 가능하나 자동 덮어쓰기 없음 |
| 일반 첨부 업로드 중 NAS 응답 유실 | `WRITE_UNCERTAIN`과 단계별 증거 기록. 이후 NAS 변경을 멈춤, 중복 업로드/자동 롤백 삭제 없음 |
| 첨부 성공 후 본문/원문 게시 실패 | NAS의 기존 본문/백업 원문과 새 파일 모두 보존. 결과 확인 절차로 전환 |
| 새 노트 생성 응답 유실 | 기존 client_request_id 영수증과 staging 증거로 노트 식별. 새 UUID로 create 재실행 금지 |
| 저장 중 새 파일 추가/본문 편집 | 진행 snapshot 변경 금지. 새 세대의 본문·manifest는 다음 저장으로 유지 |
| 취소 중 업로드 완료 응답 도착 | UI 삽입 금지. 로컬 임시 파일만 후속 취소/만료 대상. NAS 불확실 작업에 연결됐다면 pin 유지 |
| 읽기 전용·잠김·휴지통·계정 변경 | 새 업로드/저장을 거절하고 다른 owner에 재귀속하지 않음 |
| 임시 파일 만료/용량 부족 | 저장 완료로 표시하지 않음. 재선택 또는 명시적 참조 제거 후 재시도 안내 |

현재 보류 ack API는 ‘사용자가 확인했다’는 기록이며 일반 첨부의 실제 존재·무해성을 증명하지 않는다.
후속 재저장 시에도 NAS 재조회와 미해결 첨부 작업 검사를 유지한다. 안전하게 연결할 수 없는 새 파일은 보존한다.

## 9. 파일 처리와 미리보기

- 파일명은 경로로 사용하지 않는다. NUL·제어 문자·CRLF·경로 구분자를 정리하고 길이를 제한한다.
- 클라이언트 MIME/확장자는 힌트다. 인라인 이미지 유형은 서버의 시그니처와 이미지 구조/치수 검사로 확정한다.
  최대 가로·세로 8192px, 전체 32메가픽셀을 초기 제안으로 두고 압축 폭탄/불완전 포맷은 다운로드 전용 또는 거절한다.
- SVG/HTML/스크립트/알 수 없는 파일은 동일 origin에서 실행하지 않는다. 일반 파일은 attachment 다운로드만 제공한다.
- 임시·기존 다운로드 모두 owner 검사, `nosniff`, 안전한 Content-Disposition, `Cache-Control: private, no-store`를 적용한다.
- 미리보기는 인증 후 fetch한 검증 이미지로 만들며 임의 URL을 서버가 대신 받아 오지 않는다.
- bearer 임시 공개 링크를 만들지 않는다. SID/쿠키/토큰·파일 바이트·원본 파일명은 로그에 기록하지 않는다.
- 새 원문 봉투·Markdown·HTML이 맥 앱과 Note Station에서 읽히는지 확인하고, 기존 수식 자동 정리가 일반 첨부를 삭제하지 않게 별도 소유권을 유지한다.

## 11. 검증과 완료 기준

### 자동 회귀

- 텍스트 paste 유지, 이미지 paste 1회 삽입, 다중 drop 순서, 커서 이동·IME·undo/redo·노트 전환 중 늦은 응답.
- 크기·개수·설치/owner quota 경쟁, 위조 MIME/확장자, 악성 파일명, 손상·과대 이미지, Content-Length 없는 요청.
- 타 owner/draft/노트의 UUID 거절, CSRF·Origin·로그인 만료·쿠키 회전, HTTP 내부망 WebCrypto 부재.
- 같은 upload_id 재호출·응답 유실·다른 내용 재사용, 수신 중 재시작, pin 중 취소/만료 차단.
- 기존/새 노트, 같은 파일명, 여러 첨부, 수식·보존 HTML·기존 첨부 공존, 새 참조/manifest 누락·불일치.
- 업로드/본문/최종 원문의 각 NAS 단계 응답 유실·충돌·재조회 실패에서 자동 재전송·삭제가 없는지 확인.
- 저장 중 추가 편집/첨부와 새 노트 ID 재기준화, 완료된 생성 영수증이 파일 BLOB 회수 후에도 재사용되는지 확인.
- 기존 DB migration과 재시작, 암호화된 파일만 저장되는지, 회수 후 참조/증거가 남는지 검사.
- backend 전체, frontend 전체, TypeScript/프로덕션 빌드. 원문 봉투 계약 변경 시 Swift/CLI 호환 회귀도 실행.

### 실제 브라우저·NAS 검증

- 브라우저: 스크린샷 paste, PNG/JPEG/WebP/GIF, PDF·한글 이름·동일 이름 파일, 새 노트/기존 노트.
- NAS: 전용 QA 노트로 업로드·바이트 hash·제목/본문/첨부 보존 재조회, Note Station과 맥 앱에서 표시·다운로드.
- 웹→맥 편집→웹 재조회 왕복에서 일반 첨부와 수식/원문 유지.
- 브라우저 재로드, 컨테이너 재시작, 연결 끊김, 저장 중 편집과 취소 시 결과 확인.
- NAS 검증은 별도 승인된 QA 데이터만 사용하며 기존 사용자 노트나 파일을 삭제하지 않는다.

테스트가 제공하지 않는 실제 NAS 일반 첨부 계약을 mock 성공만으로 정상이라고 선언하지 않는다.
최종 완료는 브라우저 입력부터 NAS와 맥에서 재조회까지 구분해서 기록한다.
